# 浮動小数点と丸め

唯一の前置き。全章の誤差の議論がここに乗るので先に読む。薄い。

## `f64` は \\(\mathbb{R}\\) ではない

数学では実数直線は連続で、任意の2点の間に無限個の点がある。`f64` は有限集合で、
要素数は \\(2^{64}\\) より少し少ない。この差は「精度が有限」という以上のことを意味する。
演算が閉じていないし、結合的でもない。\\((\mathbb{R}, +)\\) は群だが `f64` の加算は群を作らない。
以下の章で出てくる誤差の話は、ほぼ全部この一点から出る。

### binary64 の内訳

IEEE 754 の binary64 は 64 bit を符号・指数・仮数に割る。

| 部分 | bit 数 | 役割 |
|---|---|---|
| 符号 \\(s\\) | 1 | \\((-1)^s\\) |
| 指数 \\(e\\) | 11 | バイアス 1023。格納値 \\(e\\) に対し実際の指数は \\(e - 1023\\) |
| 仮数 \\(f\\) | 52 | 先頭の 1 は格納しない（**暗黙の 1**） |

正規化数の値は

\\[
x = (-1)^s \times 1.f \times 2^{e-1023}
\\]

仮数は格納52 bit ＋暗黙の1 bit で**実質53 bit**である。Rust では
`f64::MANTISSA_DIGITS` が `53` を返す。この 53 という数が以下ずっと効く。

指数部が全0（非正規化数・ゼロ）と全1（無限大・NaN）は特別扱いで、ここに
`f64::INFINITY` と `f64::NAN` が住む。押さえておくとよい定数:

| 定数 | 値 |
|---|---|
| `f64::MAX` | `1.7976931348623157e308` |
| `f64::MIN_POSITIVE`（最小の正規化数） | `2.2250738585072014e-308` |
| 最小の非正規化数 | `5e-324` |
| `f64::EPSILON` | `2.220446049250313e-16` |

### 機械イプシロンと単位丸め——2つある

ここは用語が紛らわしく、文献によって \\(\varepsilon\\) の定義が2倍ずれる。

- \\(\varepsilon = 2^{-52} \approx 2.22 \times 10^{-16}\\)
  ——**1.0 と、1.0 の次に大きい `f64` との差**。Rust の `f64::EPSILON` はこちら
- \\(u = 2^{-53} = \varepsilon/2 \approx 1.11 \times 10^{-16}\\)
  ——**単位丸め（unit roundoff）**。最近接丸めの相対誤差の上界

誤差解析で出てくるのは \\(u\\) のほうである。基本演算 \\(\mathrm{op} \in \\{+,-,\times,\div\\}\\) について、
オーバーフロー・アンダーフローが起きない限り

\\[
\mathrm{fl}(x \mathbin{\mathrm{op}} y) = (x \mathbin{\mathrm{op}} y)(1 + \delta), \qquad |\delta| \le u
\\]

が成り立つ。「計算結果は、真の結果を相対誤差 \\(u\\) 以内で丸めたものである」——
これが以降すべての誤差解析の出発点で、[密行列の線形代数](ch02-linalg.md)の後退安定性もここから積み上がる。

丸めの既定は**最近接偶数丸め**（round half to even）である。ちょうど中間の値を常に
切り上げると誤差が一方向に溜まるので、仮数の最下位 bit が 0 になる側へ倒す。

## 桁落ち

「精度が16桁ある」は「答えが16桁合う」を意味しない。近い2数の**引き算**は、
上位の一致した桁を消し、下位に残っていた誤差を相対的に巨大化する。これを
桁落ち（catastrophic cancellation）という。

教科書的な例が二次方程式である。\\(ax^2+bx+c=0\\) の根の公式

\\[
x = \frac{-b \pm \sqrt{b^2-4ac}}{2a}
\\]

は、\\(b^2 \gg 4ac\\) のとき \\(\sqrt{b^2-4ac} \approx |b|\\) となり、\\(b\\) と符号が逆になる側の根で
分子が引き算になって桁落ちする。

\\(x^2 - 10^8 x + 1 = 0\\) がその例である（真の小さい根は \\(10^{-8}\\) にきわめて近い）。
素朴な根の公式は、小さい根の**先頭の桁から間違える**。16桁の精度が1桁も残っていない。
有効数字が減ったのではなく、情報が消えた。

回避は、桁落ちしない側の根を公式で求め、もう一方を**根と係数の関係**
\\(x_1 x_2 = c/a\\) から出す。引き算を1回避けるだけで精度が戻る。
一般則として——近い2数の引き算が現れたら、式変形で引き算を消せないか探す。
\\(\sqrt{x+1}-\sqrt{x}\\) を \\(1/(\sqrt{x+1}+\sqrt{x})\\) に、\\(1-\cos x\\) を \\(2\sin^2(x/2)\\) に、
というのが同じ話である。

## 加算は結合的でない

\\[
(0.1 + 0.2) + 0.3 \neq 0.1 + (0.2 + 0.3)
\\]

これは Rust でも Python でも C でも同じで、IEEE 754 の帰結である。等号は `false` になる。

数値解析の教科書はここで止まるが、実務ではこの先に問題がある。
総和を `rayon` で並列化すると、どの部分和がどの順で畳み込まれるかはスケジューリング次第で、
実行ごとに変わりうる。つまり同じ入力に同じコードを走らせて、結果のビットが変わる。
[有限要素法](ch08b-fem.md)で剛性行列のアセンブリを並列化するとき、これが再現性の問題として戻ってくる。

「並列化したら答えが変わった」はバグではなく、順序に依存する演算を順序の決まらない方法で
畳み込んだという定義どおりの挙動である。決定的な結果が要るなら、
畳み込み木（分割の仕方）を固定する。`rayon` の分割はワークスティールに依存するので、
分割を固定しない限り再現しない。

ここで補償付き総和に逃げてはいけない。後述の Kahan も pairwise summation も
**順序依存**である。精度は上がるが、順序が変われば結果も変わりうる——
桁範囲の広い項をシャッフルして比べると、Kahan でも結果の一致しない試行が現れる。
pairwise も同様である。
Kahan と pairwise は精度を上げる道具であって、再現性を与える道具ではない。

総和そのものを順序非依存にしたいなら、長アキュムレータや誤差なし変換に基づく
厳密総和（ReproBLAS、Rump–Ogita–Oishi など）が要る。

## 補償付き総和

\\(n\\) 個の数の素朴な総和の誤差は最悪 \\(O(nu)\sum|x_i|\\) で、\\(n\\) に比例して悪化する。
とくに**大きな値に微小値を大量に足す**と壊滅的になる。

`1.0` から始めて `1e-16` を \\(10^7\\) 回足す。素朴な総和は **`1.0`** のまま動かない。

1回の加算ごとに `1.0 + 1e-16` が `1.0` に丸まる（`1e-16` が単位丸め \\(u = 1.11\times10^{-16}\\) を
下回るため）ので、\\(10^7\\) 回の加算が**1つ残らず消える**。

**Kahan の補償付き総和**は、この「丸めで捨てられた分」を変数に取っておいて次の加算で戻す。
手続きは和 \\(s\\) と補償 \\(c\\) を持ち、各項 \\(x_i\\) について

\\[
y = x_i - c, \quad t = s + y, \quad c = (t - s) - y, \quad s = t
\\]

を回す。\\((t-s)\\) は「実際に \\(s\\) に足さった分」で、そこから \\(y\\) を引いた \\(c\\) が
「足せなかった分」になる。ここで大事なのは、この式が数学的には \\(c = 0\\) の恒等式だという点である。
実数の上では何もしていない。丸めがあるから意味を持つ。したがって
コンパイラに「最適化」されると消える——`-ffast-math` 相当が Kahan 加算を壊すという有名な話はこれで、
Rust は既定でこの種の再結合をしないので消えないが、理由を知らずに書くと危うい。

誤差は \\((2u + O(nu^2))\sum|x_i|\\) となり、\\(n\\) への依存が主要項から消える。

**Neumaier の改良**は、加える項が現在の和より大きい場合に Kahan が補償を取り損なう
ケースを直したもので、\\(|s| \ge |x_i|\\) かどうかで補償の取り方を分岐させる。
実装するならこちらが素直である。

## Rust の言語機構

ここからが言語側。数学の事実が型としてどう現れているかを見る。

### なぜ `f64: Ord` が無いのか

Rust では `f64` に `PartialOrd` は実装されているが `Ord` は実装されていない。
理由は NaN である。`Ord` は**全順序**を要求する——任意の2要素が比較可能で、
特に反射律 \\(x \le x\\) が要る。しかし

```rust
let x = f64::NAN;
assert!(x != x);        // 通る
assert!(!(x < x));      // 通る
assert!(!(x >= x));     // 通る
```

NaN はどの値とも順序関係を持たない。`PartialOrd::partial_cmp` が
`Option<Ordering>` を返して `None` を許すのは、この「比較できない組がある」を型で表しているからである。

実害として、`Vec<f64>` に `.sort()` は生えない（`sort` は `T: Ord` を要求する）。
`.sort_by(|a, b| a.partial_cmp(b).unwrap())` は NaN が1つでも混ざると panic する。

### `total_cmp` が解決するもの

`f64::total_cmp` は IEEE 754 の **totalOrder** 述語の実装で、`Ordering` を返す
（`Option` ではない）。NaN も含めた全順序を、bit パターンの順序として定義する。
性質を押さえておく。

```rust
assert_eq!(-0.0_f64, 0.0_f64);                              // == では等しい
assert!((-0.0_f64).total_cmp(&0.0) == std::cmp::Ordering::Less);  // total_cmp では -0.0 < 0.0
```

つまり `total_cmp` は `==` と整合しない。NaN にも符号があり、`-NaN < -∞ < ... < +∞ < +NaN`
という順に並ぶ。ソートしたいだけなら正しい道具だが、「数値としての大小」ではない。

### FMA

`f64::mul_add(a, b, c)` は \\(a \times b + c\\) を**丸めを1回だけ**行って計算する
（fused multiply-add）。素朴に書くと乗算で1回・加算で1回の計2回丸まる。
ハードウェアに FMA 命令があれば1命令になる。内積・Horner 法・
[常微分方程式](ch04-ode.md)の Runge–Kutta の係数合成のように「掛けて足す」が並ぶ場所で効く。

ただし結果が `a * b + c` と bit 単位で一致しない。速くて正確な演算が、
別の実装との突き合わせを壊すことがある。自作 FFT を `rustfft` と機械精度で照合するとき
（[FFT と Monte Carlo](ch07-fft-mc.md)）、この差が「合わない」の原因になりうる。

### 誤差比較の道具

`assert_eq!(x, y)` を浮動小数点でやると、数学的に等しいはずの値が丸め差で落ちる。
dev-dependency に入れてある `approx` がこれを扱う。
`assert_relative_eq!` が相対誤差、`assert_abs_diff_eq!` が絶対誤差で、
`epsilon = ` / `max_relative = ` で許容を指定する。

どちらを使うかは毎回考える必要がある。真値が 0 の近くだと相対誤差は定義が壊れる
（0 に対する相対誤差は常に 1 か無限大になる）。逆に真値が \\(10^{8}\\) のオーダーなら
絶対誤差での比較は無意味に厳しい。[根の探索](ch01-roots.md)の停止条件の話と同じ構造の問題がここにもある。

## この章で決めること

答えは書かない。

1. **`f64` の比較をどう扱うか。** ソートや `max` が要る場所で、NaN を
   「起きない前提で `unwrap`」するか、`total_cmp` で全順序に押し込むか、
   そもそも NaN が入らないことを型で保証するか
2. **NaN の伝播を型で防ぐか、実行時に弾くか。** 前者は「NaN でないこと」を
   不変条件に持つラッパ型を作る道で、構築時に検査すれば以降ゼロコストになる。
   後者は各所で `is_nan()` を見る道。API の使い勝手と、検査の抜けやすさが天秤にかかる
3. **誤差の許容をどう表現するか。** 定数で持つか、引数で受けるか、
   絶対と相対のどちらを既定にするか

## 完了条件

Kahan（または Neumaier）加算が素朴な総和より精度で勝つことを、実際に有意な差が出る入力で示す。

差が出ない入力を選ぶと「実装したが効果が見えない」で終わる。上で見た
「`1.0` に `1e-16` を \\(10^7\\) 回足す」は素朴な総和が**全部落とす**ので、
オラクルとして使える。

| 入力 | 真の値 | 素朴な総和 |
|---|---|---|
| `1.0` に `1e-16` を \\(10^7\\) 回加算 | `1.000000001` | `1.0` |

桁落ちのほうは、二次方程式の素朴な式と安定な式を両方書いて差を見る。
\\(x^2 - 10^8 x + 1 = 0\\) の小さい根で、素朴な式は `7.450580596923828e-09`、
真値は `1e-08` に十分近い（相対誤差 25%）。

# 自動微分

古典的な数値解析の canon には無いが、現代の数値計算の本質である。
**[根の探索](ch01-roots.md)で保留した「導関数をどう渡すか」の回収**であり、
**[有限要素法](ch08b-fem.md)のメッシュと同じ所有権の問題**を先に踏む章でもある。

自動微分は記号微分でも数値微分でもない。**プログラムを、微分の連鎖律に沿って
機械的に別のプログラムへ写す**操作である。誤差は丸めだけで、打ち切り誤差がない。

## なぜ差分では駄目か——実測

導関数を \\((f(x+h)-f(x))/h\\) で近似すると、誤差が2つ現れる。

- 打ち切り誤差 \\(\approx \frac{h}{2}|f''|\\)——\\(h\\) を小さくすると減る
- 丸め誤差 \\(\approx \frac{2u|f|}{h}\\)——\\(f(x+h)\\) と \\(f(x)\\) の桁落ち。\\(h\\) を小さくすると増える

和を最小化する \\(h\\) は \\(h^\* \sim \sqrt{u} \approx 10^{-8}\\) で、そのときの**相対**精度が \\(\sqrt u\\) のオーダー。
どうがんばっても精度は半分の桁しか出ない。

\\(f = \exp\\)、\\(x = 1\\)（真値 \\(e\\)）で実測すると、誤差のオーダーはこう動く:

| \\(h\\) | 前進差分の誤差 | 中心差分の誤差 |
|---|---|---|
| \\(10^{-4}\\) | \\(10^{-4}\\) | \\(10^{-9}\\) |
| \\(10^{-6}\\) | \\(10^{-6}\\) | \\(10^{-10}\\)（最良） |
| \\(10^{-8}\\) | \\(10^{-8}\\) 前後（最良） | \\(10^{-8}\\) 前後 |
| \\(10^{-10}\\) | \\(10^{-6}\\) | \\(10^{-7}\\) |
| \\(10^{-12}\\) | \\(10^{-4}\\) | \\(10^{-4}\\) |

**U 字である。** \\(h\\) を小さくするほど良くなるのは途中までで、そこから先は悪化する。

ただし**表の最良値を「理論値と一致した」と読んではいけない。** 上の誤差モデルを
最小化すると \\(h^\* = 2\sqrt{u|f|/|f''|}\\)、そのときの誤差は

\\[
E(h^\*) = 2\sqrt{u\,|f|\,|f''|}
\\]

で、実測の最良値より1桁ほど大きい。最適点の近傍を細かく走査すると誤差は**2桁以上ばらつき**、
その RMS が理論値とよく合う。表の最良値は丸めの運がよかった下側の外れ値である。
最適点の近傍で誤差がこれだけ散らばること自体が、この節で最も教育的な事実である。
（\\(\sqrt u\\) は刻み幅であって誤差ではないので、次元の違うものを並べて
「一致」と言うのは筋が悪い。桁が近く見えるのは \\(|f| \approx |f''| \approx O(1)\\) だからにすぎない。）

中心差分 \\((f(x+h)-f(x-h))/(2h)\\) は打ち切り誤差が \\(O(h^2)\\) になる。同じ最小化をすると

\\[
E(h) = \frac{u|f|}{h} + \frac{h^2}{6}|f'''|,
\quad
h_{\text{opt}} = \left(\frac{3u|f|}{|f'''|}\right)^{1/3},
\quad
E(h_{\text{opt}}) = \tfrac32 3^{-1/3}(u|f|)^{2/3}|f'''|^{1/3}
\\]

オーダーとしては \\(h \sim u^{1/3}\\)、誤差 \\(\sim u^{2/3}\\) だが、
\\(u^{2/3}\\) という数字そのものを期待しないこと——
スケール因子 \\(|f|^{2/3}|f'''|^{1/3}\\) が掛かる。上の表の最良値が理論最小より大きいのも同じ事情で、
\\(h\\) を最適点まで動かして初めて理論値のオーダーに届く。しかも前進差分と同じく近傍で散らばる。
それでも**機械精度には遠い。**

自動微分は \\(h\\) を持たない。**打ち切り誤差がゼロで、丸め誤差だけが残る。**

### ただし「打ち切り誤差がゼロ」には条件がある

正確には、**自動微分が微分するのは関数ではなくプログラムである。**
両者がずれる場合があり、どれも数値計算では実際に踏む。

1. 非平滑点。`abs` / `max` / `min` / ReLU、`sqrt` の 0 での微分は、
   実行時にたまたま通った枝の片側微分を返す。数学的な微分が存在しないのに値が返る
2. 分岐。`if x < c` を含むプログラムは区分的にしか微分できない。
   AD は分岐条件そのものを微分しないので、境界で不連続になる
3. 反復解法を貫通させる場合。[根の探索](ch01-roots.md)の Newton 法や[常微分方程式](ch04-ode.md)のソルバを AD で微分すると、
   反復回数に依存した「収束していない導関数」が出る。微分と反復の極限の
   順序交換は保証されていない

3番目は後述の「[根の探索](ch01-roots.md)・[常微分方程式](ch04-ode.md)への接続」に効く。

記号微分との違いは別にある。記号微分は式を展開するので、
\\(f = g_1(g_2(\cdots g_n(x)))\\) のような深い合成で式が指数的に膨れる（expression swell）。
自動微分は値を伝播するだけなので膨れない。

## 前進モード——dual number

\\(\varepsilon^2 = 0\\) を満たす形式的な量 \\(\varepsilon\\) を導入し、\\(a + b\varepsilon\\) の形の数を考える
（\\(\varepsilon\\) は無限小ではなく、**\\(\mathbb{R}[\varepsilon]/(\varepsilon^2)\\) の元**である）。

積は

\\[
(a + b\varepsilon)(c + d\varepsilon) = ac + (ad + bc)\varepsilon
\\]

\\(\varepsilon\\) の係数に積の微分法則がそのまま現れる。
一般に \\(f\\) を dual に拡張すると

\\[
f(a + b\varepsilon) = f(a) + b f'(a)\,\varepsilon
\\]

したがって **\\(x = a + 1\cdot\varepsilon\\) を入れて \\(\varepsilon\\) の係数を読むと \\(f'(a)\\) が出る。**
連鎖律は合成すれば自動的に伝播する。実装者が連鎖律を書く場所はどこにもない。

\\[
\begin{aligned}
(a+b\varepsilon) + (c+d\varepsilon) &= (a+c) + (b+d)\varepsilon \\\\
\sin(a+b\varepsilon) &= \sin a + b\cos a\,\varepsilon \\\\
\exp(a+b\varepsilon) &= e^a + b e^a\,\varepsilon \\\\
\frac{1}{a+b\varepsilon} &= \frac1a - \frac{b}{a^2}\varepsilon
\end{aligned}
\\]

多変数の場合、\\(\nabla f\\) の \\(i\\) 番目の成分を得るには
\\(x_i\\) だけ \\(\varepsilon\\) の係数を 1 にして走らせる。\\(n\\) 成分には \\(n\\) 回要る。

## 逆モード——テープ

出力を \\(y\\) とする。出力から入力へ向かって連鎖律を適用し、各中間変数 \\(v\\) について
随伴 \\(\bar v = \partial y/\partial v\\) を、出力側から逆向きに伝播させる。

\\[
\bar v = \sum_{w \,:\, v \to w} \bar w \frac{\partial w}{\partial v}
\\]

順方向に一度計算して計算グラフ（テープ）を記録し、
逆方向に一度なぞるとすべての入力に対する偏導関数が同時に出る。

### コストの非対称性——backprop が逆モードである理由

\\(f : \mathbb{R}^n \to \mathbb{R}^m\\) について、

| モード | コスト | 追加メモリ |
|---|---|---|
| 前進 | \\(n \cdot \mathrm{cost}(f)\\) の定数倍 | \\(O(1)\\) |
| 逆 | \\(m \cdot \mathrm{cost}(f)\\) の定数倍。**\\(n\\) に依存しない** | \\(O(\text{演算数})\\) |

逆モードの定量的な内容が **cheap gradient principle**（Baur–Strassen）である——
\\(f : \mathbb{R}^n \to \mathbb{R}\\) の**全勾配**が、\\(f\\) 1回の評価コストの
**定数倍（通常3〜5倍）で、\\(n\\) に依らず**手に入る。「\\(m\\) に比例」だけだと
\\(n = 10^9\\) のときのコストが読者に伝わらない。

損失関数はまさに \\(f : \mathbb{R}^n \to \mathbb{R}\\) で、\\(n\\) がパラメータ数（\\(10^9\\) のオーダー）、
\\(m = 1\\) である。**逆モードなら1回の逆走査で全勾配が出る。**
前進モードなら \\(10^9\\) 方向ぶんの仕事が要る（ベクトル dual で1パスに束ねられるが、
仕事量は \\(n\\) に比例したままである）。

backprop が逆モードなのは、**この一点だけが理由である。**
逆に \\(f : \mathbb{R} \to \mathbb{R}^m\\)（1つのパラメータに対する多数の出力の感度）なら
前進モードが有利で、[常微分方程式](ch04-ode.md)の感度解析にはそういう形が出る。

代償はメモリで、逆モードは順方向の中間値を全部保持する必要がある。
深いネットワークで活性値がメモリを食うのはこれで、
チェックポイント法（一部を捨てて再計算する）が使われる理由でもある。

## Rust の言語機構

この章は Rust の設計の密度が最も高い。

### 前進モードは演算子オーバーロードだけで書ける

`std::ops` の `Add` / `Sub` / `Mul` / `Div` / `Neg` を `Dual` に実装すると、
`a * b + c` がそのまま dual の演算になる。

```rust
use std::ops::Mul;
#[derive(Clone, Copy)]
struct Dual { re: f64, du: f64 }
impl Mul for Dual {
    type Output = Dual;
    fn mul(self, o: Dual) -> Dual { todo!() }  // 積の微分法則がここに入る
}
```

問題は `sin` / `exp` / `sqrt` である。これらは `f64` の**固有メソッド**であって
トレイトのメソッドではないので、`Dual` に自動では生えない。選択肢が2つ:

- 自前のトレイトを切る。`f64` にも実装すれば、ユーザ関数を
  `fn f<T: Elementary>(x: T) -> T` と書ける。**初等関数だけでは足りない**——
  算術のスーパートレイトと、`f64` の定数を持ち上げる手段が要る

```rust
use std::ops::{Add, Sub, Mul, Div, Neg};

trait Elementary:
    Copy + Add<Output = Self> + Sub<Output = Self> + Mul<Output = Self>
    + Div<Output = Self> + Neg<Output = Self>
{
    fn lit(v: f64) -> Self;   // これが無いと `x * x - 2.0` が書けない
    fn sin(self) -> Self;
    fn exp(self) -> Self;
}
```

  `lit` をユーザに書かせるのが AD の売り文句と噛み合うかは判断が要る
  （`From<f64>` をスーパートレイトにする手もある）。「この章で決めること」の1に入る
- `num_traits::Float` を実装する。エコシステムと繋がるが、実装すべきメソッドが非常に多い。
  本当の障壁はメソッド数ではなく **`Float: NumCast`** のほうで、
  `Dual` に `to_f64` を実装すると導関数部を黙って捨てることになる。意味論的な罠である

**孤児則（orphan rule）はどちらの選択肢も妨げない。** 禁じられるのは
**外部のトレイトを外部の型に**実装することだけである。

| 組み合わせ | 可否 |
|---|---|
| 自前トレイト × `f64`（選択肢1） | 合法 |
| `num_traits::Float` × 自前の `Dual`（選択肢2） | 合法 |
| `num_traits::Float` × `f64` | 不可 |

### generic にする必要があるのはどちらか

「[根の探索](ch01-roots.md)の `newton` を `f64` 固定で書いていると dual を渡せない」と考えたくなるが、**これは誤りである。**
generic であるべきなのは**ユーザ関数のほう**で、solver は `f64` 固定のままでよい。

```rust
fn newton(f: impl Fn(f64) -> f64, df: impl Fn(f64) -> f64, x0: f64) -> f64 { todo!() }

fn poly<T: Elementary>(x: T) -> T { x * x - T::lit(2.0) }   // ユーザ関数だけ generic

let root = newton(|x| poly(x),
                  |x| poly(Dual { re: x, du: 1.0 }).du,     // 導関数を手書きしていない
                  1.0);
```

これで導関数の手渡しは消える（`root` は `SQRT_2` に一致する）。したがって**この章の完了条件は、[根の探索](ch01-roots.md)を `f64` 固定で書いていても達成できる。**

では solver 自体を generic にする必要が生じるのはいつか。solver を**通して**微分したいときである
——陰関数微分、パラメータに依存する根の感度、Newton 反復を貫通する AD。
そのときは前述の「反復解法を貫通させる」問題、すなわち微分と反復の極限の
順序交換が保証されないという話に直面する。[根の探索](ch01-roots.md)・[常微分方程式](ch04-ode.md)への接続はそちらにある。

### 逆モードのグラフの所有権——この章の核心

計算グラフのノードは互いに参照し合う。素朴に書くと

```rust
struct Node { parents: Vec<Rc<RefCell<Node>>>, value: f64, adjoint: f64 }
```

**これは動くが、Rust では定石ではない。** 理由はこうである。

1. 実行時の借用検査（`RefCell`）のコストと、パニックの可能性
2. 参照カウントの更新コスト
3. **drop が親チェーンを再帰的に辿るので、長いテープでスタックが溢れる**

3番目を「循環参照でメモリが解放されない」と書きたくなるが、**この構造では循環は起きない**——
各ノードは既に生成済みの祖先だけを指すので DAG で閉じている。実害は解放時の再帰のほうである。

Rust の定石は**インデックスを持つ arena**（テープ方式）である。

```rust
struct Tape { nodes: RefCell<Vec<Node>> }
struct Node { parents: [usize; 2], partials: [f64; 2] }  // 親を「番号」で指す
```

ポインタの代わりに `usize` の添字を使う。得られるものは、
すべてのノードが1本の `Vec` に連続して乗る（キャッシュに良い）、
解放が `Vec` の drop 1回（上の再帰問題が消える）、
そして逆走査が `nodes` の逆順走査そのものになること。

内部可変性が完全に消えるわけではない点に注意する。演算子オーバーロードで
テープに push する以上、共有参照の先のどこかに内部可変性が要る。
定石は上のように **`Tape` の内側に `RefCell<Vec<Node>>` を持たせる**ことで、
そうすれば変数は `&Tape` を持つだけで済む。正確な利得は「`RefCell` が消える」ではなく
**ノード数 \\(N\\) 個の `RefCell` がテープ1個に減る**ことである。

失うものは、添字が型で守られないこと（別のテープの添字を渡せてしまう）である。
`slotmap` の `Key` のような型付きハンドルはここを埋める道具で、
世代番号を持つので「解放済みの要素を指す添字」も検出できる。

**これは[有限要素法](ch08b-fem.md)のメッシュとまったく同じ問題である。** 要素↔節点↔辺が相互参照する構造を
`Rc<RefCell<>>` で組むか、インデックス方式で組むか。
**同じ道具（`slotmap` / `typed-arena` / `petgraph`）で両方が解ける**ので、
ここで選んだものを[有限要素法](ch08b-fem.md)にそのまま持っていける。

### クレートの扱い

**デファクトが無い領域である。** `num-dual` は前進モードのみ、
`autodiff` は 2023-03 で停止している。自作が正当である。

グラフの道具のほうは確立している——`petgraph` / `slotmap` / `typed-arena`。
**汎用の道具でこの章と[有限要素法](ch08b-fem.md)の2つの問題を解く**のが狙える形である。

## オラクル

自動微分は性質テストと相性が非常によい。個別の正解を用意する必要がない。

- 中心差分との一致（`proptest`）。**許容は絶対値ではなく相対で取る**（後述）
- 解析的に微分できる関数との一致。ただし「**厳密一致」は保証できない**——
  AD の演算列と手書きの導関数式は多くの場合 bit 一致するが、しない場合がある。
  \\(x^n\\) を繰り返し乗算で組むか `powf` で組むかで、実測でも末尾数 bit が分かれる。
  **数 ulp 以内**で判定する（[浮動小数点と丸め](ch00-float.md)の FMA の話と同じ構造である）:

| \\(f\\) | \\(f'\\) |
|---|---|
| \\(x^n\\) | \\(nx^{n-1}\\) |
| \\(\sin x\\) | \\(\cos x\\) |
| \\(e^{x^2}\\) | \\(2xe^{x^2}\\) |
| \\(\sin(\exp(x))\\) | \\(\cos(\exp(x))\exp(x)\\)（連鎖律が効いているかの確認） |

- 前進モードと逆モードの一致。同じ関数を両方で微分して突き合わせる。実装の相互検証になる

### 許容は相対で取る

**絶対許容は \\(|f|\\) が大きい領域で必ず落ちる。** 上の誤差モデル
\\(u|f|/h + h^2|f'''|/6\\) の第1項が示すとおり、絶対誤差は**関数値 \\(|f|\\) に比例**するからである。

これは実験で切り分けられる。Rosenbrock に定数 \\(C\\) を足すと
\\(f'\\) は完全に不変で \\(|f|\\) だけ増える。この状態で \\(C\\) を大きくしていくと、
中心差分の絶対誤差は**桁単位で悪化する**——導関数は1ミリも変わっていないのにである。
逆に \\(f\\) 全体を定数倍すると（\\(|f|\\) も \\(|f'|\\) も同じだけ増える）相対誤差は一定に保たれる。
この2つの実験を自分でやると、依存しているのが \\(|f|\\) のほうだと確定できる。

ただし比例するのは**目安**であって各点の値ではない。\\(|f|\\) を増やしても誤差が減ることがあり、
前進差分と同じく個々の値は桁で散らばる。

Rosenbrock では \\(|f|\\) と \\(\\|\nabla f\\|\\) が同時に大きくなるので、
「勾配が大きいと落ちる」ようにも見える。だが原因は \\(|f|\\) のほうである。

広めの入力域を `proptest` 相当で叩くと、固定した絶対許容はほぼ全滅する。
純粋な相対許容も安全ではない——勾配成分だけが消えて \\(|f|\\) が残る点
（\\(y \approx x^2\\) の近傍）では、相対誤差はいくらでも大きくなる。

したがって判定は**下限つきの混合許容**にする。

```rust
// cd は中心差分、ad は自動微分の結果
assert!((ad - cd).abs() <= 1e-6 * cd.abs().max(1.0));
```

`.max(1.0)` は**真の導関数が 0 に近いときに達成不可能な精度を要求しないための絶対誤差の下限**である
（この式に除算は無いので、ゼロ割の回避ではない）。
許容の根拠は誤差モデル \\(u|f|/h\\) から出る——入力域を絞れば \\(|f|\\) の上限から
絶対誤差が押さえられ、勾配が消える点でも下限1が効く。
Rosenbrock は4次で増えるので、`proptest` の入力域は \\(|x| \le 2\\) 程度に絞るとよい。

## 完了条件

- **前進モードで[根の探索](ch01-roots.md)の Newton 法を、導関数を手渡しせずに動かす。**
  [根の探索](ch01-roots.md)が `f64` 固定でも達成できる（前述）。generic にすべきはユーザ関数のほうである
